        安全模型：漏洞会怎么出现（含两处自我修正）  v0.1
        触发：作者提问"我这个提权漏洞会不会出现？"
════════════════════════════════════════════════════════════════

────────────────────────────────────────────────────────────────
零、直接回答
────────────────────────────────────────────────────────────────

  会。但形态全变。

  更准确地说：**被消灭的是一类，转变形态的是一类，新引入的是两类 ——
  而新引入的两类里，有一类是本设计独有的、前所未有的漏洞类别。**

  ★ 本文包含对前文两处设计的修正，修正处明确标出【修正】。

────────────────────────────────────────────────────────────────
一、被消灭的漏洞类别（这部分前文成立）
────────────────────────────────────────────────────────────────

  类别                      为何消失
  ─────────────────────────────────────────────────────────────
  路径混淆 / 符号链接攻击   没有字符串路径参与授权
  setuid / suid 提权        没有"身份"可以冒名
  ACL 配置错误              没有 ACL
  TOCTOU（检查-使用竞争）   检查与使用是同一个对象，无时间窗
  探测型信息泄漏            不存在的名字在视图里根本不存在
  "以管理员身份运行"滥用    没有身份，只有能力
  sudo 配置错误             没有 sudo

────────────────────────────────────────────────────────────────
二、转变形态的漏洞（没消失，只是换了目标）
────────────────────────────────────────────────────────────────

  ── 2.1 内核（本源）缺陷 ────────────────────────────────────

    提权的目标从"变成 root"变成"**让本源替你签名**"。

    · 一次内核缺陷 = 全盘失守（本源是唯一权柄源）
    · 无法用设计消除，只能：
        a) 内核只留三机制（攻击面极小 —— 这正是内核准则的另一个理由）
        b) 长期走形式化验证（seL4 式路线）

  ── 2.2 衰减链的验证漏洞 ────────────────────────────────────

    能力的"限制条件"如果表达成一个链，那么**校验这条链的代码**成为关键。

    · 校验器写错一个分支 → "只读"限制可以被摘掉 → 等价于提权
    · 对策：
        a) 限制的表达语言必须**极小且可判定**（不做通用表达式求值）
        b) 用 MAC（消息认证码）让任何篡改**在密码学上可检测**
           （即使校验器有 bug，篡改也过不了 MAC 验证）

  ── 2.3 换皮的混淆代理（confused deputy）────────────────────

    分身 A 持有能力 X，被诱导"替 C 去用 X"。

    · 这是能力系统的经典问题，答案是"**不代做，只传能力**"
    · 本设计里必须由语言强制：函数签名显式声明所需能力（无全局符号表）
    · 于是"代做"在语法上就不成立 —— 因为函数拿不到它没声明的能力

────────────────────────────────────────────────────────────────
三、【修正】新类别一：能力会随数据被复制到全世界
────────────────────────────────────────────────────────────────

  ── 3.1 前文的设计错误 ──────────────────────────────────────

    前文（新推导 v0.1 第二节）我这样写：

      "能力对象 = 内容寻址的数据 + 签名，可持久化、可存入其它对象"

    ★ 这个设计有洞：

      **如果能力是内容寻址的普通对象，那么分享数据 = 分享能力。**

    ── 3.2 攻击场景 ──────────────────────────────────────────

      某人把一张"能读财务数据"的能力对象，无意间嵌进了一份文档对象
          ↓
      文档被分享（内容寻址 → 任何拿到哈希的人都能取到）
          ↓
      能力跟着文档一起复制到全世界，而且是"合法传播"

    ★ 这比 Unix 的权限泄漏严重得多，因为**内容寻址的本意就是"复制免费"**。
      旧世界的句柄天然不可复制（是内核表项）；新世界的能力如果做成明文
      数据，就自动获得了"可自由复制"这个致命属性。

    ── 3.3 修正方案（两条，都要）──────────────────────────────

    修正 A：**封印能力（sealed capability）**

      能力不是明文，而是**用持有者公钥加密的封装**。

        · 复制这个 blob **毫无用处** —— 只有私钥持有者能解封
        · 于是"可持久化"与"不可被冒用"同时成立
        · 类比：旧世界能力是"句柄"（不可复制）；
                新世界能力是"密文"（可复制但无用）

    修正 B：**线性能力（linear capability）**

      语言类型系统强制"使用即消耗"（affine/linear 类型）：

        · 能力类型**不可序列化、不可复制、不可嵌入数据对象**
        · 用完即失效（需要再次使用时必须重新取得）
        · 由编译器强制，不是靠约定

    ★ 两条的关系：
      修正 A 解决"存储与传输"，修正 B 解决"程序内部误用"。
      缺任何一条，能力泄漏都会成为主要攻击面。

────────────────────────────────────────────────────────────────
四、【全新】新类别二：时间可回退 vs 撤销不可回退
────────────────────────────────────────────────────────────────

  ── 4.1 这是本设计独有的漏洞类别 ────────────────────────────

    攻击场景：

      1. 某条能力被撤销
      2. 一个分身回到**撤销之前**的那个态
      3. 在那个态里，那条能力还在
         → **撤销被"回到过去"绕过了**

    ★ 时间旅行直接给了攻击者一条绕过所有撤销的通道。
      这类漏洞只可能在"时间是坐标"的系统里出现 —— 没有任何历史系统
      需要处理这个问题，因为它们没有可回退的系统状态。

  ── 4.2 修正：一条新公理 ───────────────────────────────────

    ┌──────────────────────────────────────────────────────────┐
    │  公理 4 修订：                                            │
    │     时间可回退，权柄不可回退。                             │
    │     （Time is reversible. Authority is not.）             │
    └──────────────────────────────────────────────────────────┘

  ── 4.3 实现方式：墓碑集合 ──────────────────────────────────

    · **态**：可回退（历史永远可得）
    · **墓碑集合**（已撤销的能力）：**全局单调**，只增不减，
      **不属于任何态**
    · 投影规则：

          任何时间坐标的投影 = 应用墓碑集合 → 再应用那一刻的态
          （顺序不可交换）

    推论：
      · "回到过去"永远无法复活已撤销的能力
      · 撤销成为一条**单调、可审计**的日志，与态的历史完全解耦
      · 撤销的代价是 O(1)（加一条墓碑），不是遍历历史

  ── 4.4 顺带解决的另一个问题：撤销的竞态 ────────────────────

    旧世界"撤销"往往是先检查后使用（撤销竞态）。
    在本设计里，引用解析与使用是**同一次跳转**（一个 ^），
    且投影时必然先行应用墓碑集合 —— 竞态窗口消失。

────────────────────────────────────────────────────────────────
五、新增可验证断言（接 A1–A36）
────────────────────────────────────────────────────────────────

  A37 [能力不可随数据泄漏]
      把能力对象嵌入数据对象并分享给另一个分身
      → 接收方**必须无法使用它**（修正 A + 修正 B 的联合验收）

  A38 [时间不可复活权柄]
      回到撤销之前的态 → 被撤销的能力**仍然不可用**

  A39 [墓碑单调]
      墓碑集合在任何操作序列下只增不减；尝试删除一条墓碑必须失败

  A40 [不代做]
      构造"分身 A 试图替分身 C 使用 C 的能力"的测试集
      → 全部必须失败，且失败原因统一为"未持有该能力"

  A41 [封印能力可复制无害]
      复制封印能力 blob 到任意位置，未持有私钥者解封必须失败

  ★ A38 是本项目**独有**的断言类别：
    它验证的不是功能，而是"时间维度上的安全不变式"。
    没有回退能力的系统根本不需要测这个。

────────────────────────────────────────────────────────────────
六、诚实的残余风险（能力模型解决不了的）
────────────────────────────────────────────────────────────────

  R1  内存安全、并发竞争、整数溢出、解析器缺陷、写错的业务逻辑
      → 能力模型不解决这些，需要语言层面的安全设计
  R2  密钥丢失与被窃
      → 删掉"用户"概念后，密钥成为事实上的身份。
        管理方案（生成/备份/恢复/转移）是待决项 F6，尚未解决
  R3  本源自身的缺陷
      → 无法用设计消除，只能靠内核最小化 + 形式化验证
  R4  社会工程
      → 任何模型都防不住"有人自愿把能力给出去"

  一句话：**能力模型消灭的是"权限模型的错误"，不是"程序的错误"。**
