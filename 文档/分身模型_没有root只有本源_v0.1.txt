────────────────────────────────────────────────────────────────
零、作者的原话与本文的任务
────────────────────────────────────────────────────────────────

  作者原话：
    "有没有 root？我在想能不能直接借用内核。内核就是 root，
     内核分出了一个天道，他就是 user，一个被限制的。"

  任务：把它形式化，并检查它与已有公理、已定机制是否冲突。

  结论先行：
    · 这个想法**不需要新增机制** —— 它就是"可衰减能力"（前文第二节）
      的自然推论，只是方向反过来看
    · 它消掉的不只是"root"这一个概念，而是**一整个概念层**
      （用户、账户、组、登录、提权、管理员身份）

────────────────────────────────────────────────────────────────
一、大道（root of authority）
────────────────────────────────────────────────────────────────

  定义：
    大道 = 系统中**唯一能签发能力**的东西。实现上就是内核本身。

  要点：
    · 大道不是"一个用户"，它是**权柄的源头**，没有身份属性
    · 大道不参与日常操作，只在"签发/撤销"时被触及
    · 系统启动 = 大道签出第一个天道（初始天道）
    · 之后所有天道，都由已有天道派生（能力衰减），大道不介入

  与既有公理的关系：
    公理 5（能力即引用）+ 前文第二节（能力对象可衰减、可持久化）
    → 大道只是"衰减链的起点"，不引入任何新机制。

────────────────────────────────────────────────────────────────
二、天道（projection）—— 形式定义
────────────────────────────────────────────────────────────────

  ┌───────────────────────────────────────────────────────────┐
  │  天道 = {  视图（可见的名字映射）                            │
  │           能力集（持有的能力对象集合）                       │
  │           父引用（它是从哪个天道派生出来的）                 │
  │         }                                                  │
  └───────────────────────────────────────────────────────────┘

  与"用户"的根本区别：

    用户： 先有身份 → 再按身份查权限表 → 决定能做什么
    天道： **没有身份** → 手上有什么能力 → 就能做什么

  派生（授权）的规则：
    · 只能**衰减**（派生出不超出自身能力的子集）
    · 派生出的能力带签发者签名，可追溯完整链
    · 撤销 = 从视图移除那条"名字 → 能力"的边

  诚实标注（不假装新）：
    天道 ≈ KeyKOS/EROS 里的 domain（一个 domain 就是一个能力集合）。
    新的部分在于：**能力可持久化 + 天道的能力集本身是可因果的对象**，
    因此天道可以被版本化、被审计、被回滚。KeyKOS 的能力不能持久化。

────────────────────────────────────────────────────────────────
三、由此自动消失的概念（不是"不实现"，是"不存在"）
────────────────────────────────────────────────────────────────

  概念            在旧世界的形态             在本模型中
  ──────────────────────────────────────────────────────────────────
  root            全能账户                   不存在。有大道，但没有"root 用户"
  管理员          root 或 sudo 组             持有"管理能力"的天道 —— **岗位，不是身份**
  登录            认证 → 建立会话             不存在。开机由大道签出初始天道
  账户/用户表     /etc/passwd、SAM            不存在。没有"账户"这个对象
  组              gid、SID                   不存在。共享靠传递同一个能力
  提权            setuid / sudo / 内核漏洞     不存在。特权只能被授予，不能凭空获得
  权限提升漏洞    常见攻击类别                 **原理上不存在**（见第四节）

────────────────────────────────────────────────────────────────
四、原理级推论：提权漏洞这个类别消失了
────────────────────────────────────────────────────────────────

  Unix 里提权漏洞能存在，前提是**存在一条从低权到高权的路径**：
    setuid 位、内核接口缺陷、配置错误、可写服务 …

  本模型里没有这条路径：

    天道想获得它没有的能力
      → 唯一途径是"另一个持有者签给它"
      → 没有"绕过"，因为没有可绕过的介质（字符串路径不参与授权）

  于是攻击面收缩为一项：**大道本身（内核代码）的实现缺陷**。

  ★ 这不是"权限模型的问题"，而是"内核实现的问题"——
    边界变干净了。这也意味着：内核的代码质量成为唯一的关键，
    这一点恰好与"自重建内核、内核保持可审计"的准则方向一致。

────────────────────────────────────────────────────────────────
五、四个漂亮的连锁结论
────────────────────────────────────────────────────────────────

  1. 系统启动 = 权柄向下传播
     大道签初始天道 → 初始天道派生系统天道 → 系统天道派生应用天道
     启动过程本身就是一棵"能力派生树"，可完整审计

  2. 重启 = 天道消失，本体还在
     所有天道都是投影，重启只是收回投影。这解释了为什么
     "系统状态"与"存储内容"是两件事（前者是投影，后者是对象）

  3. "谁做的"这个审计问题变成"用了哪条能力链"
     每个天道的能力集是可因果对象 → 审计日志 = 一串能力链对象
     可验证、不可篡改、可离线复核（对应断言 A24）

  4. 隔离的边界是天道，不是用户
     内存保护 = 天道地址空间；名字可见性 = 天道视图；
     两者天然一致，不需要"用户态/内核态 + uid 检查"这种双重机制

────────────────────────────────────────────────────────────────
六、诚实的代价（三条，都不小）
────────────────────────────────────────────────────────────────

  C1  现实接口无法直接映射
      SSH 的公钥登录、sudo、POSIX 的 chown/chmod、文件权限位、
      systemd 的用户服务 … 全部对不上。
      → 必须提供"兼容视图"（对应待决项 D7），这是落地的硬性前提。

  C2  密钥归属（待决 F6）
      身份只在"需要签名"时出现，那么"我的密钥"归谁？
      技术上归"那组能力的持有者"，不是账户。
      → 实际管理（生成、备份、恢复、转移）需要一套新方案。

  C3  工具链全部要重写
      没有"以某身份运行"，要模拟别人就得换一个天道。
      更清晰，但 ps/top/权限诊断类工具全部重做。

────────────────────────────────────────────────────────────────
七、新增可验证断言（接 A1–A24）
────────────────────────────────────────────────────────────────

  A25 [无 root 概念]  源码与二进制符号中不得出现 root/sudo/setuid/uid/gid/
                     账户/登录等概念用词（反向断言，搜到即失败）

  A26 [派生只能衰减]  任意天道尝试派生出超出自身能力的能力 → 必须失败

  A27 [无提权路径]    构造一个"低权天道试图获得未授予能力"的测试集，
                      全部必须失败；且失败原因必须统一为
                      "未持有该能力"（不是"权限不足"，见 §4.3）

  A28 [启动即派生树]  记录一次完整启动：所有天道必须能追溯到一个父引用，
                      最终汇聚到大道；出现"无父"— 失败

  A29 [天道可审计]    任一天道的能力集可导出为对象，篡改后校验失败；
                      且能由该对象完整重建该天道的可见视图

  ★ A25 与 A21 是同一类反向断言：它们不验证"功能存在"，
    而验证"某个概念确实消失了"。这类断言是本项目独有的验证手段。
