零、诚实边界（写在最前面，否则整篇作废）
────────────────────────────────────────────────────────────────

  作者要求：一个也不要抄。

  我能承诺的和不能承诺的：

  ✗ 不能承诺：所有零件都是新的。
     零件在物理上不可能凭空生出来 —— 能力来自 KeyKOS，内容寻址来自
     Git/Venti，快照来自 ZFS，可复现构建来自 Nix，时态数据库来自
     Snodgrass 的双时态模型。

  ✓ 能承诺：**排列方式完全重新推导，不照抄任何系统的架构。**

  本文的每一个结论，都由"公理 + 一个必须解决的问题"推出来，
  而不是"某某系统是这么做的，我们也这么做"。

  ★ 判断"是否照抄"的唯一标准：
    去掉所有专有名词后，本系统还有没有独立的推理链。

────────────────────────────────────────────────────────────────
一、核心洞察：所有系统都在假装"现在"不需要讨论
────────────────────────────────────────────────────────────────

  观察（这是整篇设计的起点）：

    · Unix / Windows：系统状态是"现在"，历史靠备份这类外围手段抢救
    · ZFS / btrfs：快照是**存储层**的能力，与计算无关
    · Git / Nix：历史是**工具层**的概念，不是系统的维度
    · 时态数据库：时间是一等公民，但它管的是**数据**，不是**系统**

  没有任何一个系统，把"时间"当作**内核的第一等维度**来设计整套机制。

  这留下一个巨大的空位。本设计就落在这个空位上。

────────────────────────────────────────────────────────────────
二、三机制：态 / 迹 / 视
────────────────────────────────────────────────────────────────

  ┌──────────────────────────────────────────────────────────────┐
  │  态（tài）  对象图的一次完整快照。身份 = 该图的哈希。         │
  │  迹（jì）   态与态之间的转移。**本身也是对象**（有哈希）。     │
  │  视（shì）  从某个态出发、按某个视角投影出的可见世界。        │
  └──────────────────────────────────────────────────────────────┘

  ── 2.1 态 ──────────────────────────────────────────────────

    定义：态 = 系统全部可达对象的集合的一次快照，身份为其整体哈希。

    要点：
      · 没有"当前状态"这个全局事实。系统**没有现在**。
      · "现在"只是某个视的一个参数（见 2.3）。
      · 态可寻址 → 可比较、可回滚、可传输、可离线复核。

  ── 2.2 迹 ──────────────────────────────────────────────────

    定义：迹 = 一次转移的记录对象：

        迹 = { 前态哈希, 后态哈希, 能力链, 分身引用, 数据 }

    要点：
      · 一次计算不是"正在运行的东西"，而是**一条迹**。
        系统里没有"运行中"，只有"已经发生的转移"。
      · 迹是一等对象 → **可分叉**（同一起点走两条）、
        **可合并**（找共同祖先）、**可审计**（谁、用哪条能力链）
      · 计算 = 迹的延伸。**"进程"这个概念在此消失。**

  ── 2.3 视 ──────────────────────────────────────────────────

    定义：

        视 = { 态坐标（哪一刻）
               时间坐标（视角落在哪一刻）
               名字映射（可见的名字 → 引用）
               能力集（持有的能力对象）
             }

    要点：
      · **时间是视的参数，不是系统的属性。**
      · 于是"看三天前的系统"与"看现在"是**同一个操作**，只是参数不同。
      · 一个视是一个投影；投影是可撤销、可审计的（分身模型）。

────────────────────────────────────────────────────────────────
三、由此塌掉的一整套概念（这是"厉害"的具体含义）
────────────────────────────────────────────────────────────────

  概念       旧世界                         本设计
  ────────────────────────────────────────────────────────────────────
  文件       有位置、有名字、可变           对象（有哈希，无位置）
  进程       有 pid、有状态、会消失         迹（历史，永不消失，可分叉）
  现在的状态 全局唯一的事实                 视的一个参数
  用户       身份 + 权限表                  能力链
  备份       额外工具、额外流程             指一个坐标
  快照       存储层功能                     态本身
  回滚       危险操作、需要工具             换一个坐标
  安装/卸载  修改系统、有残留               从态到态的一条迹
  升级       可能搞坏系统                   新迹；旧态永远还在
  补丁       改动现场                       新迹
  **调试**   **复现 → 定位 → 修复**          **回去 → 分叉**
  日志       事后记录、可能被篡改           迹本身（内容寻址，不可篡改）

  ── 3.1 最狠的一条：调试消失 ────────────────────────────────

    调试之所以存在，唯一的原因是：**过去不可达。**

    当过去可达时：
      "复现"这个动作没有意义 —— 你直接回到那一刻
      "定位"变成图查询 —— 问"这个字节是哪条迹写的"
      "修复"变成分叉 —— 从那一刻开一条新迹，原迹保留

    ★ 注意这不是"调试更方便了"，而是**这个活动本身不再需要存在**。

────────────────────────────────────────────────────────────────
四、新手会问的问题，全部失去形状（"看不懂"的可操作定义）
────────────────────────────────────────────────────────────────

  "看不懂"有两种。我们只要第二种：

  ✗ 表层看不懂：符号不认识 → 等价于乱码，无价值
  ✓ 深层看不懂：**每个词都认识，但问题本身不成立**

  新手提问                        在这套系统里的真实情况
  ─────────────────────────────────────────────────────────────
  "我的文件在哪？"                没有"在哪"。只有引用，没有位置
  "哪个进程在跑？"                没有"在跑"。只有迹（已经发生的转移）
  "系统的当前状态是什么？"        没有"当前"。只有视（参数化的投影）
  "谁改了这个？"                  没有"谁"。只有能力链（可查询的三元组）
  "怎么回滚？"                    没有"回滚"。只有换坐标
  "怎么安装这个？"                没有"安装"。只有从态到态的转移
  "怎么调试这个 bug？"            没有"调试"。只有回去并分叉
  "权限不够怎么办？"              没有"权限"。只有是否持有能力
  "这是文件还是目录？"            没有这个二分。只有对象与关系

  ★ 一个系统的"新"，可以用一句话检验：
    **它能让多少个旧问题失去形状。**
    上表列了九个。这是本项目"新"的量化指标。

────────────────────────────────────────────────────────────────
五、三机制对语言的要求（新语必须同构）
────────────────────────────────────────────────────────────────

  ── 5.1 效果标记 ! 获得了精确含义 ───────────────────────────

    在前文，! 表示"有副作用"。现在它能被精确定义：

        纯函数      = 不延伸迹（不产生新的态）
        ! 标记函数  = **会延伸迹**（产生一个新态）

    于是效果标记不再是一个约定，而是**系统模型的直接投影**。

  ── 5.2 函数签名必须声明它读取的坐标 ───────────────────────

    因为时间是视的参数，而视必须显式传入（无全局符号表），
    函数签名要能表达"我在哪个时间坐标上工作"。

  ── 5.3 无法表达的东西 ─────────────────────────────────────

    新语里**不能写**出这些概念（因为系统里不存在）：
      进程 / pid / 用户 / 权限检查 / 安装 / 覆盖写 / 全局变量

    ★ 这不是"不推荐"，是**语言里没有对应的语法**。

────────────────────────────────────────────────────────────────
六、内核准入准则的最终形态
────────────────────────────────────────────────────────────────

  前文定的准则是"内核只装重建系统所必需的"。现在它可以更精确：

  ┌──────────────────────────────────────────────────────────────┐
  │  内核只提供三样机制：                                         │
  │      1. 存取态（对象与引用）                                  │
  │      2. 延伸迹（态到态的转移）                                │
  │      3. 投影视（态 + 时间坐标 → 可见世界）                    │
  │  加上一样元能力：本源签发/撤销能力（分身模型）。              │
  │  其余一切（含三件套的复杂部分）都在外面。                      │
  └──────────────────────────────────────────────────────────────┘

  这个内核面积极小，而且**每一样都能回答"重建系统时用在哪里"**（A22）。

────────────────────────────────────────────────────────────────
七、新增可验证断言（接 A1–A29）
────────────────────────────────────────────────────────────────

  A30 [态可寻址]     给定任意历史态哈希，能投影出一个**可继续运行**
                     的分身（不是只读快照 —— 必须能从那一点往前走）

  A31 [迹可分叉]     从同一祖先态出发走两条迹，互不影响；
                     且能计算两条迹的差异

  A32 [时间是参数]   同一对象在两个不同时间坐标下投影结果不同，
                     且差异可解释（能说出是哪条迹造成的）

  A33 [无"运行中"]   源码与二进制符号中不得出现 process/pid/task 类概念
                     （反向断言：搜到即失败）

  A34 [因果可查询]   任取一个字节，能追溯到 (迹, 能力链, 分身) 三元组

  A35 [旧态永存]     任意次数的变更之后，最初的态仍可投影出可运行分身

  A36 [迹不可篡改]   篡改任意一条迹对象 → 校验失败（内容寻址的直接推论）

  ★ A30 是最难的一条，也是最关键的一条：
    "可回滚"很容易做成"只读快照"，那样毫无意义。
    必须做到"回到过去，并且从那里继续走" —— 这才是时间成为一等公民。

────────────────────────────────────────────────────────────────
九、待决（不假装完成）
────────────────────────────────────────────────────────────────

  H1  外部世界的时间锚定：物理时钟、网络中断、外部事件
      如何进入"态"？（这是整套设计最大的未解问题，必须正面解决）
  H2  IO 的非确定性：读一个设备、收一个包，如何表达成"迹"？
  H3  性能：每步都产生新态，代价多大？需要多粗的粒度？
  H4  实时性要求的场景（音频/显示）如何在这种模型下工作
  H5  空间回收：态永不消失与存储有限之间的矛盾（GC 策略）
  H6  与外界的兼容视图（D7）在时间模型下如何定义
  H7  "迹"的粒度：一次系统调用？一次函数调用？一次事务？
  H8  多核并发：两个核同时延伸迹 → 需要合并语义（CRDT？串行化？）

  ★ H1 与 H8 是硬骨头。本文不回避：这两块没解决之前，
    本设计不能声称"已完成"。
