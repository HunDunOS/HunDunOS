        回答：混沌的调度器是怎么实现的
                                    2026-10-03
════════════════════════════════════════════════════════════════

  提问："不知道，你的调度器怎么实现的？"

  直接回答：**没有调度器。而且连中断都是关着的。**

  下面把证据、原因、以及"真要做会长什么样"一次说清。


────────────────────────────────────────────────────────────────
一、证据（都可以自己验证）
────────────────────────────────────────────────────────────────

  × 没有 sti   —— 引导器里 cli 之后，内核再没开过中断
  × 没有 IDT   —— 连中断描述符表都没有，中断根本递不进来
  × 没有进程/线程 —— 内核源码里搜"调度 / 进程 / 线程 / 上下文切换"，一处都没有

  内核入口就三行（反汇编出来的）：

        _start:
            mov  esp, offset _kernel_stack_top
            call _gfx_init
            call _rt_cls
            call fn_主              ← 进去就再没出来

  而"主"是这样：

        主()      = 终端主(); 停机()
        终端主()  = 初始化; xh { 印("HD> "); 读行(); 分词(); 执行() }
                                            ↑ 死循环（新语的 xh 就是 while）

  **键盘、鼠标、时钟全是轮询**：
      · PIT 计数器   直接读端口 0x40（先锁存再读）
      · 键盘/鼠标    直接查端口 0x64 的状态字

  也就是说：**"打断"这件事在内核里根本不存在**。
  而调度器的前提（时间片中断）也就不存在。


────────────────────────────────────────────────────────────────
二、这不是"漏做了"，是跟设计一致的
────────────────────────────────────────────────────────────────

  常规操作系统的调度器，调度的东西叫**进程 / 线程**。
  而混沌的设计里【没有进程】。

  有的是**分身（projection）**：

        分身 = { 视图（可见的名字映射）
                 能力集（持有的能力对象集合）
                 父引用（它是从哪个分身派生出来的）
               }

  而设计规范里有一条公理：

        【公理 7】变更原子：视图切换是单一原子动作（换一个映射引用）。

  **这句话本身就是"换用户上下文"的意思。**

  所以在这个模型里：

        "上下文切换"  退化成  "换一个引用"

  没有进程，就没有"要被调度的对象"；没有调度对象，调度器自然无从谈起。


────────────────────────────────────────────────────────────────
三、真要做，长什么样
────────────────────────────────────────────────────────────────

  最小调度器要四样东西，现在【一样都没有】：

    ① 时间源       PIT / APIC 定时器 + IDT + 开中断       ❌ 全没有
    ② 每分身一个栈   现在只有 _kernel_stack 一个             ❌
    ③ 寄存器保存/恢复  不存就切出去回不来                    ❌
    ④ 换"上下文"    视图引用 —— 视图还没做实                🔧

  但第 ④ 条跟 Unix 的差别是本质性的：

    ┌────────────┬──────────────────────┬────────────────────────┐
    │            │  Unix                │  混沌                  │
    ├────────────┼──────────────────────┼────────────────────────┤
    │ 切换什么    │ CR3（换页表基址）     │ 视图引用（一个 dword） │
    │            │ + 栈 + 寄存器        │ + 栈 + 寄存器          │
    │ 代价        │ 要刷 TLB，很重        │ 换一个引用，很轻        │
    │ 为什么      │ 每进程一个地址空间     │ 没有地址空间，只有视图  │
    └────────────┴──────────────────────┴────────────────────────┘

  所以理论上，混沌的上下文切换**比 Unix 便宜一个数量级**。

  ⚠️ 但这个结论**只在"视图真的做实"之后才成立**。
     现在视图还没做实，所以这句话暂时是空头支票 —— 不能拿它当已实现的事实说。


────────────────────────────────────────────────────────────────
四、我的建议：先别做抢占式
────────────────────────────────────────────────────────────────

  三条理由：

  1. 现在做的事根本不需要它
     画桌面、存对象、读盘，全是"一件事做完再做下一件"。

  2. 加了会先带来一堆真问题
     两个分身同时改同一个视图怎么办、要不要锁、内存序怎么保证 ——
     这些比"把多个分身跑起来"更早咬人。

  3. 跟模型打架
     抢占意味着"写到一半被换出去"，
     而整个模型建立在"同一时刻只有一个视图在动"上。

  建议先做【协作式】：不是抢占，而是"分身主动让出"（yield）。

    · 让出点正好是那些"要等外部事件"的地方：等键盘、等盘、等压缩跑完
    · 跟"只追加、不可变"合拍：没有抢占，就不会有半路写坏
    · 实现量小：让出() = 存一个续点 + 换视图引用 + 跳过去，**不需要定时器**


────────────────────────────────────────────────────────────────
五、一句话
────────────────────────────────────────────────────────────────

     现在没有调度器，是因为**还没有"要被调度的东西"**。

     在混沌里那个东西叫【分身】，
     而分身的"上下文"**就是一个引用**。

     先把视图做实，调度器是自然结果；
     反过来先写调度器，调度的就是空气。


────────────────────────────────────────────────────────────────
附：这套东西现在的实测状态（2026-10-03）
────────────────────────────────────────────────────────────────

  内核真实占用：text 60435 + data 494 + bss 51908 = 112837 字节 ≈ 110 KB
               （比 L2 缓存还小 → 整个工作集早就全在缓存里）

  内核是【可拆】的：13 个目标文件，不要哪个就从链接命令行删掉即可
  最底层汇编只剩 原语.asm（1296 字节目标文件）：端口读写 + 内存读写 + CPUID + 停机

  已经跑通的：
    · 自研引导器 → VBE → 保护模式 → 自研引导协议
    · 盘格式（超级块 / 对象区 / 索引区 / 轴区），写进去、重启、按哈希取回来一字不差
    · 内容去重（同一内容存两次 → 同一个哈希，盘上只占一份）
    · 删除/撤销 = 换引用，对象一个字节没动
    · LZSS 压缩（译自 0BSD 源码）：110 → 26 → 110，逐字节一致

  没做的：视图做实、包格式、GC、多核、调度器
