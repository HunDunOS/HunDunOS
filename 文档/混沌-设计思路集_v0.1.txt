一、定位：三家的符号
────────────────────────────────────────────────────────────────

  作者原话：
    "win \  unix /  我^"

  展开：
    Windows   \   路径是树的地址，分隔符是向下
    Unix      /   路径从根出发，分隔符是向下
    混沌      ^   路径是一次能力跨越，符号是"向上"

  ^ 和 / 的根本差别是【根】：
    Unix 的 / 隐含"存在一个根"
    ^ 不隐含任何根 —— 每个 ^ 都是一次可失败、可审计、可撤销的能力跨越

  落到哪了：🔧 有设计（设计规范 v0.1 第 2.1 节），没实现。
    编译器现在把 ^ 当"指针解引用"（还得写在 wx{} 里），完全是另一个意思。

二、核心：一切皆哈希
────────────────────────────────────────────────────────────────

  作者原话：
    "Linux 是一切全是文件，我的是 一切全是哈希"
    "对了 Linux 是。一切全是文件我的是。一切全是哈希"

  含义：身份 = 内容哈希。名字就是内容，内容一变名字就变。

  白送的好处（不需要额外机制）：
    · 去重          同名即同内容，盘上/内存里只占一份
    · 完整性        哈希不对就取不出来，静默损坏不可能
    · 版本历史      改 = 产生新对象，旧的还在
    · 撤销          换回旧引用，原子，不需要 undo 日志
    · 缓存/同步     同名就是同一个，不用判断

  落到哪了：✅ 已实现并实测（内存版 + 盘上版）
    实测数据：混沌 → 0xCCDD9C6D   一切皆哈希 → 0x30AA4C83   hello → 0x4F9F2CAB
    与 Python 独立实现逐字节对得上。

三、改名 / 删除
────────────────────────────────────────────────────────────────

  作者原话：
    "gm 改名字。回去检查哈希。然后覆盖"
    "那删除的" / "删除怎么用？"

  三步（改名）：
    ① 改名    改的不是对象，是【映射】。对象一个字节没动。
    ② 回去检查哈希   目标在不在（引用即能力）；新映射自己的哈希；查重（有就不写）
    ③ 覆盖    全盘只有一处覆盖：超级块里"当前视图根引用"那个字段
              覆盖的是【引用】，不是数据

  删除：
    删除 = 从【我的视图】里摘掉一个引用。对象还在，别人还看得到。
    删除和撤销删除是【同一个操作】，方向不同而已。
    全系统唯一不可逆的事：往轴上追加墓碑。

  三种强度：
    shan 名字    从我的视图摘掉              ✅ 随时换回
    jin 哈希     写进封锁集，新视图引用会被拒  ⚠️ 只有老的活视图还看得到
    加密删钥     内容加密存，删密钥            ❌ 唯一真不可逆的

  落到哪了：
    ·✅ 内存版的对象区（存/取/列/改名/删/撤销）在桌面里跑通了
    ·✅ 盘上版（混沌盘）能存能取，重启还在
    ·🔧 视图层（多视图、切换、墓碑、封锁集）没做实
    ·❓ 加密删钥没设计

九、★ 超级玩法：多虚拟内存
────────────────────────────────────────────────────────────────

  作者原话（原样记录）：
    "我在思考我们可不可以多内核，可不可以内存也是多内存。等一下我想的超级玩法
     常规的是这样的，常规的是一个薰衣草，而我的这个可不可以这样子？
     多虚拟内存，然后共存到一个文件夹里面。每个都放一点，每个都能读取。
     一个虚拟内存里面有多个虚拟内存，多个虚拟机可以同时被读取。
     CPU的话也可以让他多行读取。每个可以做一个或者是每个可以并排的一起
     工作一个东西。但是要留出一两个进行帮助其他的其他工作"

    "别人顶多是单的，而我的是多虚拟内存。这样子可以让cpu读取的更快，
     因为是小部分的，可以读取更多。这个可行性吗"

  ── 我拆成五条来评估 ──────────────────────────────────────

  ① 多内核 / 多内存 → ❓ 词要换
     不是"多内核"（那叫虚拟化：hypervisor + 两级页表，天价）
     不是"多内存"（根本不需要）
     是 ——【一个内核 + 多视图】
       一个对象区（唯一）+ N 个视图（每个 = 一组锚点 + 一个映射引用）
     理由：视图只是几十字节；对象是共享的。切换视图 = 换一个引用 = O(1) 原子。
     ⚠️ 要紧的是：一旦说"虚拟内存"，脑子里就会冒出页表、地址空间、缺页中断，
        然后设计就会跑偏。这套模型里【没有地址空间这个东西，只有视图】。

  ② 共存到一个文件夹 → ✅ 位置已经有了
     盘上 LBA 2 就是"视图记录区"（我早留好了），只是还没做实。

  ③ 嵌套（一个虚拟内存里有多个）→ 🔧 天生成立，靠公理 6
     映射即对象 → 映射本身可以被引用 → 视图里放一个指向子视图的锚点即可。
     【不需要虚拟化】—— 没有 hypervisor，没有两级页表，就是"引用了一个引用"。

  ④ 每个都能读取 → ✅ 正是设计文档里的【分身模型】
     分身 = { 视图, 能力集, 父引用 }
     本源（= 内核）是唯一能签发能力的东西
     所以：不是"多个内核"，是"本源签出多个分身"
     "每个做一个 / 并排干同一个" = 能力集的重叠程度决定的

  ⑤ 留一两个帮忙 → ❓ 换个说法更对
     不是"留个空闲核"，是【留一个后台分身】：
       视图 = 只有对象区 + 混沌盘；能力 = 读全部、追加、不能删
       任务 = GC（标记清扫）· 哈希校验 · 压缩
     而且校验/压缩都是纯函数（输入确定→输出确定），并行没有竞争。

  ⑥ CPU 多行读取 → ⚠️ 排最后，而且对上面全无帮助
     多视图【不需要多核】（视图切换 O(1)）
     多核要做的：APIC 初始化 → 唤醒 AP → 每核栈 → 调度
     而且现在整个运行时（_rt_*、图形、控制台）都是单核假设，全要重审。

  ── ★ 关于"分片能读得更快"：我判断【不成立】──────

     作者的理由："因为是小部分的，可以读取更多" → 让 CPU 读得更快

     为什么不对：
       · CPU 按【64 字节缓存行】读，不分片也那样读。分片大小对缓存行没有任何影响
       · 分片反而多一层间接：引用 → 查映射 → 数据（2 跳 vs 1 跳）
       · 总量不变、带宽不变 —— "读得更多"不成立
       · Unix 的页表也是这个毛病，所以才需要 TLB 兜底

     关键数字（我们自己的系统）：
         text 60435 + data 494 + bss 51908 = 112837 字节 ≈ 110 KB
         而 L2 缓存是 512KB ~ 1MB
       **我们整个内核比 L2 还小 → 早就整个在缓存里了**
       分片能带来的局部性收益，在这里等于零。

     你直觉里【真正对】的三件事（机制不一样）：
       · 工作集小 → 命中率高   这叫【局部性】，靠"按需装载"，不是分片
       · 零拷贝              拿到引用就是拿到数据 ✅ 已经是这样了
       · 去重免费 → 装得多    省的是【空间】，不是【时间】

     真正能提速的是：
       ① 缓存局部性  ② 去掉间接层  ③ 零拷贝 ✅已有  ④ 少层数 ✅已有  ⑤ 多核
       —— 我们有 ③④ 是白拿的。**快在"层数少"，不在"分得细"。**

     所以："多视图"值得做，但理由应该是【隔离 + 权限 + 共享不复制】，
     不是【性能】。

  ── 落到哪了 ────────────────────────────────────────────
     ✅ 一个对象区（内容寻址，内存 + 盘上各一份）
     🔧 视图记录区（盘上留了位置，没做实）
     ❌ 多视图、视图嵌套、视图并发规则、后台分身、多核 —— 全没做

  ── 我建议的优先级（和作者想法略有出入，写在下面供否决）──
     1. 视图做实（建/切/并列）  ← 它同时是 GC 的地基，见第十节
     2. 视图的并发规则（CAS）    ← 定错了后面全返工，比多核重要一个量级
     3. 索引区改成"索引本身也是对象"（现在还是扁平表，临时态）
     4. 轴区做实 + 墓碑 + GC
     5. .bao 打包
     6. 多核 ← 最后，且对上面全无帮助

十、作者没提到、但我认为必须先回答的：GC
────────────────────────────────────────────────────────────────

  不可变 + 只追加  →  盘只会越来越大
  无全局根（公理 3） →  可达性【不能】从 "/" 遍历

  设计给的解法：从【视图记录区】出发做可达性分析。

  所以这条链是硬的：
     视图记录区做实  →  GC 有起点  →  系统能长期活下去

  也就是说：【"视图做实"不只是"多环境"的地基，它同时是 GC 的地基。】

  另外要留位置的两件事：
    · 墓碑无限膨胀 → 需要"纪元折叠"（把旧墓碑压成一个纪元哈希）
    · 真要删隐私数据 → 加密删钥，这个必须在设计阶段就留位置，不能事后补
