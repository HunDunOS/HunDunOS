────────────────────────────────────────────────────────────────
零、作者定下的三条硬规则（不可协商，本文全部围绕它们展开）
────────────────────────────────────────────────────────────────

  规则 R1  编译器必须能被 GCC（或等价的原生工具链）构建出来。
           即：编译器本身是一份 C 源码，用现有工具链编译得到可执行文件。
           → 这是"从零"的合法起点：从零不等于从真空。
           → 这条同时锁死了自举路径（见第二节）。

  规则 R2  系统开机自带三件东西，且只需要这三件：
             ① 取源器   能取到源码
             ② 写码器   能写东西
             ③ 编译器   能编译
           → 系统的最小可用形态 = 这三件 + 内核。

  规则 R3  写码器（编辑器）不用现成思路，要新设计，
           而且它本身要用新语写、由新语编译器编译出来。
           → 即：三件套里至少一件是"自举产物"，系统才能自己长大。

────────────────────────────────────────────────────────────────
一、为什么 R1 是幸运的（而不是妥协）
────────────────────────────────────────────────────────────────

  "从零"有两种理解，必须分清：

    ✗ 错误理解：一切都必须由我发明，包括汇编器、链接器、C 编译器
      → 这条路会吃光所有时间，且没有验证手段，最终必然烂尾
      → 我们刚查过的三个项目，全都栽在"没有验证手段"上

    ✓ 正确理解：**自举门槛必须低，但自举链条必须完整可见**
      → 第一环可以用别人的工具（GCC），但之后每一环都必须由自己产出，
        且每一环都要能被验证是"自己的东西做出来的"

  历史上所有成功的自举语言都这么干：
    Rust    最初用 OCaml 写的编译器，后来自举
    Go      最初用 C 写的编译器，后来自举
    Zig     最初用 C++ 写，后来自举
    TinyCC  自身极简，能编自己

  ★ 关键洞察：本系统有内容寻址（公理 2），
    于是"自举是否可信"这个问题，有了一个**别人给不出的答案**：

        用 stage1 编译自己 → 得到 stage2
        若 stage2 的哈希 == stage1 的哈希，则自举可信

    主流语言要靠"可复现构建"外加一堆工具才能验这件事；
    本系统天然就能验，因为一切对象都有哈希。
    这是世界观公理直接转化成工程能力的第一个例子。

────────────────────────────────────────────────────────────────
二、编译器链路（stage0 → stage1 → stage2）
────────────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────────┐
  │ stage0   用 C 写的 新语 编译器（xyc.c）                       │
  │          构建方式：gcc/clang 直接编                            │
  │          产出：xyc（原生可执行文件）                           │
  │          能做什么：把 .xy 编译成 x86_64 汇编/对象              │
  │          不能做什么：还不能编自己（因为自己是 C）              │
  └─────────────────────────────────────────────────────────────┘
                              ↓ 用 stage0 编译
  ┌─────────────────────────────────────────────────────────────┐
  │ stage1   用 新语 写的 新语 编译器（内部称 编译器.xy）          │
  │          构建方式：xyc( stage0 ) 编译器.xy → 编译器对象        │
  │          产出：一个由新语产出、能编新语的编译器                │
  └─────────────────────────────────────────────────────────────┘
                              ↓ 用 stage1 编译自己
  ┌─────────────────────────────────────────────────────────────┐
  │ stage2   stage1 编译 编译器.xy 的结果                         │
  │          验收：hash(stage2) == hash(stage1)                   │
  │          相等 → 自举成立，且构建可复现                          │
  └─────────────────────────────────────────────────────────────┘

  里程碑与断言：
    M-a  stage0 能编出"hello 串口"           断言：串口输出匹配
    M-b  stage0 能编出 stage1                断言：stage1 能编出可运行程序
    M-c  stage1 能编出 stage2                断言：hash 相等
    M-d  把 stage0 从仓库里删掉，项目仍能自举  断言：只用新语源码可重建

  ★ M-d 是"从零"最硬的证据：**当你能删掉 C 编译器那一环时，才算真的自举。**

────────────────────────────────────────────────────────────────
三、三件套不是三个程序，是一个闭环
────────────────────────────────────────────────────────────────

        ┌──────────────┐
        │  取源  qy     │  从远端视图取对象（按哈希）
        └──────┬───────┘
               │ 得到源码对象（哈希即校验）
               ▼
        ┌──────────────┐
        │  写码  xm     │  结构化编辑，每次改动即产生新对象
        └──────┬───────┘
               │ 得到新源码对象
               ▼
        ┌──────────────┐
        │  编译  by     │  产出可执行对象，装进当前视图
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │   运行/验证   │  失败则回到写码，成功则可再取源
        └──────────────┘

  这个闭环的含义：**系统唯一的增长方式是"取来 → 改写 → 编译 → 验证"。**
  没有"安装包"，没有"补丁"，没有"升级"——
  因为一切变更都是"产生新对象 + 换引用"（公理 1、7）。

  与三件套对应的三个锚点（开机即可见）：

      @^取源        远端对象源（网络视图）
      @^写码        本地编辑视图
      @^编译        编译器对象（自带）

────────────────────────────────────────────────────────────────
四、三件套放在哪：内核内 还是 系统镜像内（重要决策）
────────────────────────────────────────────────────────────────

  作者的话是"可能会写进内核里面"。我作为架构师的判断：

  ── 方案甲的代价（真放进内核 ring0）：──────────────────────

    · 编译器是**解析不可信输入的巨型攻击面**（词法/语法/代码生成
      动辄上万行），放进内核等于把这块攻击面抬到最高权限
    · 内核体积与耦合度暴涨；编译器崩溃 = 整机崩溃
    · 违背七条公理的精神：内核应该是**最小机制提供者**，
      不是"什么都装进去"的容器（HaoOS 就是栽在"什么都往里塞"）

  ── 方案乙（我推荐）：三件套放在系统镜像内，由内核以三个锚点呈现 ──

    · 体验完全一样：**开机就有，不需要安装，不需要联网，随时可用**
    · 内核保持最小：它只提供"视图 + 能力 + 对象存储"这三样机制
    · 编译器崩了只是它自己崩，系统还在
    · 仍然可以满足 R3（写码器用新语写、由新语编译）

  ── 折中方案丙（如果作者坚持"必须在内核里"）：──────────────

    内核内只放**最小编译能力**：一个只够编译"编译器本身"的子集编译器，
    其余工具（写码器、取源器的复杂部分）在镜像里。
    这样内核里的那部分小到可审计，同时保留了"开机即自举"的仪式感。

  ★ 决策记录（ADR-001）
    议题：三件套放置位置
    选项：甲 全在内核 / 乙 全在镜像 / 丙 内核放最小子集
    取舍：安全性与内核最小化 vs "开机即自带"的仪式感
    暂定：**乙**（镜像内 + 三个锚点），保留升级到丙的余地
    否决条件：作者明确要求"内核二进制里必须能看见编译器代码"

────────────────────────────────────────────────────────────────
五、取源器 qy（第一件）
────────────────────────────────────────────────────────────────

  核心洞察：在这个系统里，**"下载"这个动作消失了。**

  因为对象身份 = 内容哈希（公理 2）：
    · 你请求的是"哈希 h 的对象"，不是"某个 URL 上的文件"
    · 因此**校验是请求的一部分，不是请求之后的额外步骤**
    · 传输出错、被篡改、被替换 → 哈希对不上 → 直接失败，不存在"验签"环节

  形态：
      qy 名字^版本              从当前远端视图取
      qy 名字^版本 @远端锚点      指定从哪个远端视图取
      qy h:9f3c...             直接按哈希取（最原始、最可信的形式）

  与"包管理器"的根本差别：
    · 没有"包"这个概念 —— 只有对象
    · 没有"依赖解析" —— 依赖就是被引用的对象，取的时候就一起取
    · 没有"仓库" —— 只有一个远端视图（一组锚点）
    · 没有"版本冲突" —— 两个版本是两个不同哈希的对象，天然共存

  ★ 这一条会让熟悉 Nix 的人当场愣住：连 Nix 都还需要"channel/registry"来
    把名字映射到哈希；本系统连这个都不需要，因为名字只活在视图里。

────────────────────────────────────────────────────────────────
六、写码器 xm（第二件，也是"新思路"那一件）
────────────────────────────────────────────────────────────────

  ★ 本节的每一句都直接来自七条公理，不是"想个花招"。

  ── 6.1 它不是文本编辑器，是**对象编辑器** ─────────────────

    因为对象自带类型标签（第六节对象格式），编辑器**知道你在写什么**。
    它不把源码当字符流，而是直接操作结构。

    用户看到的效果：
      · 不存在"语法错误"这个阶段 —— 结构上无法表达非法程序
      · 不存在"格式"问题（缩进/空格）—— 结构决定形状
      · 补全不是"猜"，是"这个位置允许哪些类型"

  ── 6.2 没有"保存"────────────────────────────────────────

    这是最反直觉、也最震撼的一条：

        每一次按键改动，就已经是一个持久的、有哈希的对象。

    · 没有 Ctrl+S，因为没有"未保存状态"这种东西
    · 没有"另存为"，因为改名只是换一个映射里的键（§4.3）
    · 崩溃不会丢东西，因为改动从来没有停留在内存里等你保存

    ★ 类比：Nix 里"没有 install"，本系统里"没有 save"。
      这两个"没有"是同一类设计——把过程本身变成持久对象。

  ── 6.3 撤销 = 指回旧引用（免费）──────────────────────────

    因为不可变（公理 1），历史从来没丢。撤销不是"反向操作"，
    而是"把视图里的引用指回上一个对象"。

    · 撤销是 O(1)，而且**永不出错**（不需要逆运算）
    · 可以撤销到任意历史点，不只是几步之内
    · 可以"分叉"：从三天前的版本开一条新线，两条线都留着

  ── 6.4 没有"文件树"，只有"对象图 + 类型"────────────────

    · 打开方式由**类型标签**决定，不由扩展名决定（§4.5）
    · 侧栏不是目录树，是**当前视图的映射**（名字 → 对象）
    · 同一个对象出现在多个名字下是常态（别名，§4.6），不是异常

  ── 6.5 "跳转到定义"是一次真正的视图跳转 ─────────────────

    在主流 IDE 里，跳转到定义是工具在文件集合里搜索。
    在这里，它就是一次 **`^` 能力跨越**：

        你从一个锚点跳到另一个锚点，看那里提供的映射。

    这意味着：
      · 你可以跳到"另一个视图里"的定义（跨视图导航，天然支持）
      · 这次跳转是可审计、可撤销的（因为它是一次能力跨越）
      · 跳不过去不是"找不到" —— 是"你的视图里没有那个名字"

  ── 6.6 编辑即编译 ────────────────────────────────────────

    因为编译器就在系统里（R2），编辑器可以**始终**在后台用编译器
    对当前对象做检查，且不需要"保存后编译"这一步（因为已经持久了）。

    用户看到的效果：错误在"你造出这个结构的瞬间"就出现，
    不是在你按下编译键之后。

  ── 6.7 它自己就是用新语写的 ─────────────────────────────

    这是 R3，也是"系统能自己长大"的前提：
    写码器由编译器编译，而编译器将来由写码器改写。
    到这一步，三件套形成一个自我维持的环。

────────────────────────────────────────────────────────────────
七、编译器 by（第三件）
────────────────────────────────────────────────────────────────

  ── 7.1 在系统里，编译器的输入输出都是对象 ─────────────────

    输入：源码对象（有哈希）
    输出：可执行对象（有哈希）+ 诊断对象（有哈希）

    推论：**可复现构建是免费的。**
      相同源码哈希 + 相同编译器哈希 + 相同参数 → 输出哈希必然相同
      不需要额外工具，不需要"重新构建验证"，哈希本身就是证据。

  ── 7.2 诊断消息也用系统的语义 ────────────────────────────

    错误消息不使用"权限不足""文件不存在"这类旧词汇，而使用
    §4.3 定义的三种：

        名字不存在 / 能力已撤销 / 锚点不可达

    这样连报错都在教世界观 —— 用户每次踩坑都在被提醒"这里不是 Unix"。

  ── 7.3 编译过程的可见性 ──────────────────────────────────

    编译的每一个阶段（词法 → 语法 → 语义 → 代码生成）都产出中间对象，
    全部有哈希、全部可检视。失败时能精确定位到"哪一阶段的哪个对象"。

    ★ 对比：主流编译器把中间表示藏在内存里，本系统把它变成一等对象。

────────────────────────────────────────────────────────────────
八、新增可验证断言（接 A1–A10）
────────────────────────────────────────────────────────────────

  A11 [R1] stage0 必须能被 gcc/clang 直接构建，构建命令不得超过两条
  A12 [自举] hash(stage2) == hash(stage1)
  A13 [自举·硬化] 删除 stage0 的 C 源码后，仅凭 .xy 源码仍可重建（M-d）
  A14 [取源] 篡改传输中的一个字节 → 取源必须失败，且错误为"对象哈希不符"
  A15 [写码·无保存] 编辑后直接断电（注入故障）→ 重启后改动仍在
  A16 [可复现] 同一源码 + 同一编译器 → 两次构建输出哈希相同

  ★ A15 是"没有保存"这条设计的真实验收：能做到，才配说"无保存"。
