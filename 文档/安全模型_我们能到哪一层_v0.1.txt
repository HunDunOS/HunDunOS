        安全模型：我们能到哪一层   v0.1
       （作者目标："和他一样安全，但可以比他高级"）
════════════════════════════════════════════════════════════════

────────────────────────────────────────────────────────────────
零、先把话说准
────────────────────────────────────────────────────────────────

  作者目标："把我的编译器写得和 Rust 一样安全，但可以比他高级。"

  本文的任务不是"贬低 Rust"，而是：
    1. 把"安全"分层，说清 Rust 在哪一层
    2. 指出本系统的公理让哪些错误**可以做到不可表示**
    3. 定下我们自己的语法与规则（不抄）
    4. 诚实标出 Rust 仍然更强的地方

────────────────────────────────────────────────────────────────
一、安全的四个等级
────────────────────────────────────────────────────────────────

  等级              做法                        代表
  ────────────────────────────────────────────────────────────
  ① 无检查          什么都不管                  C
  ② 运行时检查      跑起来才发现                Java / Go（边界检查）
  ③ **编译期检查**  **编译不过**                **Rust**（目前公认最强）
  ④ **不可表示**    **错误状态根本写不出来**    本系统的目标

  ★ Rust 做到了 ③，而且做得极彻底（空间安全 + 零成本抽象 + 工程成熟度）。
    我们不贬低它。我们的机会在于：**本系统的公理本身就在消除错误状态**，
    因此可以往 ④ 走。

  ★ 关键区分：
    ③ 是"编译器证明你错了" —— 你写了错的东西，被拒绝。
    ④ 是"你根本写不出错的东西" —— 错误的表示形式在类型系统里不存在。
    ④ 比 ③ 强，因为它不依赖编译器检查得是否完备。

────────────────────────────────────────────────────────────────
二、本系统能做到"不可表示"的五处
────────────────────────────────────────────────────────────────

  错误类别          别人怎么防                本系统怎么让它不可表示
  ──────────────────────────────────────────────────────────────────────
  数据竞争          Rust：Send/Sync 标注      **不可变默认（公理 1）**
                    + 借用检查                → 没有可变别名，竞争写不出来

  悬垂引用          Rust：生命周期参数        **内容寻址 + 对象不消失（公理 2）**
                                              → 引用指向的东西不会"不存在"

  跨地址空间访问    C/Rust：无此概念（UB）    **指针自带出处**
                                              → 类型层面即非法

  未授权访问        ACL/权限位（运行时）      **能力即类型（公理 5）**
                                              → 拿不到能力就编译不过

  跨时间使用        ❌ 没有任何语言有此概念    **引用绑定到态（时态内核）**
                                              → 跨态引用是类型错误

  ★ 最后一行是真正的分水岭：
    **Rust 的安全是"空间"的（内存）；
      本系统的安全是"时空 + 权限"的。**

────────────────────────────────────────────────────────────────
三、我们自己的符号（不抄）
────────────────────────────────────────────────────────────────

  @x            共享引用（只读）
  @!x           独占引用（可写）
  ^p            解引用读
  ^p = v        解引用写（编译器要求 p 是独占引用）
  wx { ... }    危险块（对应别的语言的 unsafe）；只有这里才能
                解引用原始指针、做指针算术
  qv 名 { ... } 显式区域（可选；通常由编译器推断，不需要手写标注）

  ★ 符号的自洽性（这是本设计的重点）：
    `!` 在本体系里一直表示"有副作用"，而**写操作正好是副作用**。
    所以 `@!` 不是一个新发明的标记，而是同一含义在新位置的应用。
    —— 一套符号，一个含义，贯穿始终。别家做不到这一点。

────────────────────────────────────────────────────────────────
四、六条规则（每条对应一条可验证断言）
────────────────────────────────────────────────────────────────

  规则 1  不可变默认
          bl 绑定不可写（已实现，断言 A2 已通过）
          kb 才可写，且必须显式声明

  规则 2  独占写入
          写只能通过 @! 引用；
          @! 存活期间禁止存在其它指向同一对象的引用（共享或独占）
          → 这就是"借用检查"，但用我们的符号表达

  规则 3  无悬垂
          引用不能指向存活期更短的区域。
          区域由编译器**推断**（区域偏序关系），
          **不需要像 Rust 那样手写生命周期参数** ← 标注负担更低

  规则 4  无跨空间
          指针自带出处（属于哪个地址空间/视图）；
          跨空间解引用 = 编译错误

  规则 5  无数据竞争
          发给另一个分身的引用只能是"只读"或"隔离"；
          可变引用不可共享
          → 比 Rust 的 Send/Sync 更细：按引用模式而不是按类型标注

  规则 6  危险可数
          所有原始指针操作必须在 wx 块内；
          wx 块的数量与位置可被工具枚举与审计
          → 可以对外公布"内核里 wx 块 X 个、占代码 Y 行"
          → Rust 的 unsafe 统计是**统计**；我们的可以是**强制**（编译器不让漏）

────────────────────────────────────────────────────────────────
五、新增可验证断言（接 A1–A63）
────────────────────────────────────────────────────────────────

  A64 [悬垂]        构造"引用比对象活得久"的程序 → 必须编译失败
  A65 [双重可变]    两个 @! 同时指向同一对象 → 必须编译失败
  A66 [跨空间]      x 空间指针在 y 空间解引用 → 必须编译失败
  A67 [危险块]      在 wx 块外解引用原始指针 → 必须编译失败
  A68 [竞争]        把可变引用发给另一个分身 → 必须编译失败
  A69 [跨态]        引用跨越两个态使用 → 必须编译失败
  A70 [能力]        调用未声明能力的函数 → 必须编译失败
  A71 [危险统计]    枚举一个模块：输出 wx 块数量、行数、占总行数比例
                    （元断言：这个数字必须可复现）
  A72 [无标注]      通过 A64–A70 的测试程序中，
                    **不得出现任何手写的生命周期/区域标注**
                    （证明"区域推断"这条路真的走通了）

  ★ A72 是"比 Rust 更高级"的可操作定义：
    如果同一批安全检查，我们不需要用户写标注，那就是实打实的改善。
  ★ A71 是把"安全程度"变成数字。别人可以争论理念，
    但"内核里只有 3 个 wx 块"是事实。

────────────────────────────────────────────────────────────────
六、诚实：Rust 仍然更强的地方
────────────────────────────────────────────────────────────────

  1. 生态与工具链
     cargo / crates.io / 调试器 / LSP / 文档 —— 十年工程积累，
     不是设计能追上的

  2. 借用检查器的成熟度
     Rust 的规则是在无数次实战里磨出来的，边界情况处理得很细
     我们的规则一定会有更难的边界问题（尤其与"时间坐标"结合时）

  3. 社区与人才
     语言的价值有一半在"有多少人用"

  ★ 结论：**我们的优势在模型，不在成熟度。**
    要赢的方式不是"声称全面超越 Rust"，而是
    **把模型做到别人做不到的地方**：
      · 时间维度（跨态安全）
      · 权限维度（能力即类型）
      · 标注负担（区域推断而非生命周期参数）
      · 危险可强制（wx 块可枚举、可断言）

────────────────────────────────────────────────────────────────
七、实施顺序（不要一次做完）
────────────────────────────────────────────────────────────────

  阶段 1（语言内，无需内核）
    · 规则 1：已完成（bl/kb + 断言 A2）
    · 规则 2：@ / @! 引用与别名检查 ← 下一步做这个
    · 规则 6：wx 块与危险统计

  阶段 2（需要一点运行时）
    · 规则 3：区域推断与悬垂检查

  阶段 3（需要系统模型）
    · 规则 4：指针自带出处
    · 规则 5：能力模式与分身间传递
    · 规则 7：引用与态绑定（时间安全）

  ★ 建议：阶段 1 的三条现在就能做，而且不依赖内核。
    做完就能说"新语在空间安全上已经追上 Rust 的骨架"，
    而时间与权限两条是别人没有的。
