────────────────────────────────────────────────────────────────
零、推导方法（本文所有结论的来路，必须写在最前面）
────────────────────────────────────────────────────────────────

  不比谁功能多，只做三件事：

    1. 把历代系统拆成"原子"（每个系统真正贡献的那一个机制）
    2. 看每个原子**天生缺什么** —— 缺的那块，就是后来所有人打补丁的地方
    3. 补上那块，并检查补完之后是否与已有原子冲突

  ★ 本文件不声称"从真空发明"。所有原子都来自已有系统，
    新的部分只在于"组合方式"与"补上的那一块"。
    这正是诚实性要求：**新的组合是真新，但没有凭空长出来的零件。**

────────────────────────────────────────────────────────────────
一、六代系统的原子表（以及每一代缺的那块）
────────────────────────────────────────────────────────────────

  代次   系统                    贡献的原子                      天生缺的那块
  ────────────────────────────────────────────────────────────────────────────
  1      Unix                    统一"字节流"接口                名字空间是全局的
                                 引用与名字分离（open→fd）       → TOCTOU、符号链接攻击
  2      Multics                 单级存储：内存与文件同类         太重，被"更差的赢"淘汰
  3      Plan 9                  每进程命名空间                  名字解析本身授予权限
                                 协议即文件系统（9P）
  4      KeyKOS/seL4/Fuchsia     能力 = 唯一授权途径              能力不能持久化
                                 无环境权限（no ambient authority） （只是内核句柄，重启即散）
  5      Git / Nix               内容即身份                      哈希会泄漏权限
                                 引用可持久化（哈希）             （有哈希就能取到）
  6      Macaroons / Biscuit     能力可离线衰减（加限制→更弱能力） 只在 Web 授权层用过，
                                                                 从未进入操作系统

  ── 观察（这条是整篇推导的支点）────────────────────────────

    每一代都在弥补同一个东西：**名字与引用混在一起。**

      · Unix      用权限位补救       · Windows  用 ACL 补救
      · Plan 9    用命名空间补救     · 能力系统 用"不许用名字"补救

    所有人都在打同一个补丁，只是补的位置不同。

────────────────────────────────────────────────────────────────
二、推导：把五条原子拼起来，得到"可持久化能力对象"
────────────────────────────────────────────────────────────────

  拼装过程（每一步都只用上表里的原子）：

    取原子(4) 能力是唯一授权途径        ← 不可伪造
    取原子(5) 引用可持久化（内容寻址）   ← 可存储、可备份、可去重
    取原子(6) 能力可离线衰减            ← 可派生更弱版本
    取原子(1) 引用与名字分离            ← 名字不再具有任何授权含义

  合起来就得到一个此前不存在的东西：

  ┌────────────────────────────────────────────────────────────┐
  │                  能力对象（Capability Object）              │
  │                                                            │
  │   {  目标对象哈希  +  授权链描述  +  签发者签名  }           │
  │                                                            │
  │   · 内容寻址  → 可持久化、可存入其它对象、可备份、天然去重   │
  │   · 带签名    → 不可伪造                                     │
  │   · 可衰减    → 派生"只读""只能写前 1KB"等更弱版本            │
  └────────────────────────────────────────────────────────────┘

  ★ 关键区别：
      能力系统（代 4）的能力**只是内核句柄**，不能当数据存下来；
      内容寻址系统（代 5）的哈希**可以存下来，但不携带授权**（有哈希即有权）。
      本设计把两者合一：**能力既是可持久化的数据，又是不携带授权就无法使用的凭证。**
      这是"30~100 块钱"所在的位置——前人给过零件，没人这样拼过。

────────────────────────────────────────────────────────────────
三、由此自动产生的四个结论（不是设计选择，是必然推论）
────────────────────────────────────────────────────────────────

  ── 推论 1："权限检查"这个动作消失 ─────────────────────────

    检查 = 验证这个能力对象是否有效
         = 一次对象读取 + 哈希校验 + 签名链校验

    因为你要用的引用和你验证的引用**是同一个对象**，中间没有时间窗：

      · TOCTOU（检查时/使用时不一致）**不存在**
      · 符号链接攻击、路径穿越 **不存在**（没有字符串路径能参与授权）

  ── 推论 2：撤销 = 从视图移除名字 ─────────────────────────

    持久化的能力不会自己消失，所以撤销不能靠"销毁句柄"。
    撤销的对象是**视图里那条"名字→能力"的边**（公理 7：变更原子）。

  ── 推论 3：审计变成免费的、可验证的 ───────────────────────

    每一次 ^ 跳转产生一个**路径对象**（有哈希）。
    → 审计日志本身是内容寻址的：可验证、不可篡改、可离线复核。
    → 不需要"可信日志服务"，哈希就是证据。

  ── 推论 4：**"用户"这个概念被删掉了** ─────────────────────

    主流系统：你是谁（uid/gid/SID） → 据此决定你能干什么
    本系统：  **你手上持有什么能力 → 你能干什么**

    身份只在"需要签名"时出现，不作为操作系统的核心概念。

    ★ 结果：没有账户、没有组、没有"登录"、没有"权限提升"、
      没有"root"、没有"管理员"。
      这不是省掉几个数据结构，是**删掉一整个概念层**。

────────────────────────────────────────────────────────────────
四、语言侧对应物（新语必须同步）
────────────────────────────────────────────────────────────────

  因为系统模型如此，语言必须同构，否则用户会在语言里绕开它。

    · 能力是一等类型（不是句柄、不是整数）
    · 函数签名必须显式列出它需要的锚点/能力 → **没有全局符号表**
    · "借用"概念升级为"能力派生/衰减"：
        给一个只读能力、给一个只能写前 N 字节的能力、给一个只能读一次的能力
    · 函数默认纯（效果必须用 ! 标注，见规范 §4.9）：
        因为副作用往往就是"修改视图"，而视图变更是原子动作，值得显式化

  ★ 于是语言的"陌生感"有了内在理由：
    不是"我换了个符号"，而是**同一段代码在这套世界观下必须写成另一个样子**。

────────────────────────────────────────────────────────────────
五、引擎级原理：自重建内核（ADR-001 的裁决）
────────────────────────────────────────────────────────────────

  ── 5.1 原来的问题 ─────────────────────────────────────────

    三件套（取源/写码/编译）放在哪？
      甲 全在内核   → 攻击面巨大，编译器崩溃=整机崩溃，违背"内核最小机制"
      乙 全在镜像   → 安全，但丢掉"开机即自举"的仪式感
      丙 内核放最小子集 → 折中

  ── 5.2 换一个判据（不是折中，是新准则）────────────────────

    ┌──────────────────────────────────────────────────────────┐
    │  内核准入准则：                                            │
    │  内核只装"重建整个系统所必需、且不可再分"的东西。          │
    │  其余一律在外面。                                          │
    └──────────────────────────────────────────────────────────┘

    这条准则同时回答了两个老问题：
      · "什么该进内核？"      → 重建系统必需的
      · "什么不该进内核？"    → 除此之外的一切（包括"看起来很酷"的）

    由此得到内核的形态不再是"微内核"式的（为隔离而最小化），而是：

        自重建内核（self-rebuilding kernel）
        内核自带的东西，刚好够它在没有任何外部工具的情况下重建自己。

  ── 5.3 裁决 ───────────────────────────────────────────────

    ADR-001 采纳**丙**，但性质改变：不再是妥协，而是准则的必然结果。

      · 内核内：刚好够编译"编译器本身"的最小子集编译器
      · 内核外（镜像内）：写码器、取源器的复杂部分、标准库
      · 内核保持可审计（子集编译器规模可控）
      · 保留"开机即自举"的完整仪式感

    升级条件（触发则重新裁决）：
      若最小子集编译器超过 X 行（X 待定，建议 5000），
      则退回方案乙，并把"内核是否需要编译能力"重新提交 ADR。

  ── 5.4 这条准则带来的连锁收益 ─────────────────────────────

    · 再也不用纠结"这个功能要不要进内核"—— 有判据了
    · 内核二进制的大小有了解释（不是"尽量小"，是"刚好够重建"）
    · "从零构建"这件事有了物理保证：**内核里就有重建工具**

────────────────────────────────────────────────────────────────
六、新增可验证断言（接 A1–A16）
────────────────────────────────────────────────────────────────

  A17 [能力=对象]     能力对象可以被存入另一个对象、取出、传输后仍然有效
  A18 [不可伪造]      手工构造一个伪造能力对象 → 使用必须失败
  A19 [可衰减]        由"读写"能力派生"只读"能力后，
                      用它执行写操作 → 必须失败
  A20 [无 TOCTOU]     在"验证"与"使用"之间插入任意篡改 → 操作必须失败
  A21 [无身份]        遍历整个系统：不存在"登录"、"用户表"、"root"这类概念
                      （反向断言：搜索源码与二进制符号，不得出现对应用词）
  A22 [内核准入]      统计内核二进制导出的符号：每一个都必须能回答
                      "它在重建系统时被用在哪里"；答不上来的即为违规
  A23 [自重建]        在一个只有内核的运行环境中，仅用内核自带工具
                      重建出完整系统（这是"从零"的终极验收）
  A24 [审计]          任意一次 ^ 跳转都能导出一条可验证的路径对象，
                      且篡改该对象后校验失败

  ★ A22 是一条"元断言"：它把架构准则变成了可以跑的红灯绿灯。
    这在主流系统里几乎没有先例。
