        混沌 (HunDun) 与 HDGX
        盘格式 · 包格式 · 以及为什么不需要包管理器
              v0.1
════════════════════════════════════════════════════════════════

────────────────────────────────────────────────────────────────
零、一句话
────────────────────────────────────────────────────────────────

  **NTFS 是树，ext4 是树，HDGX 是图。**

  这个差别会把身份、修改、历史、完整性、去重全部带着变。
  因此 HDGX 严格说不是"文件系统"，而是
  **内容寻址的对象存储 + 一条单调轴**。

────────────────────────────────────────────────────────────────
一、对照：三种盘格式的根本分歧
────────────────────────────────────────────────────────────────

  维度           NTFS                ext4                第 1 代
  ──────────────────────────────────────────────────────────────────────
  结构           目录树 + MFT        目录树 + inode       **对象 DAG（图）**
  身份           路径 / MFT 记录号   路径 / inode 号      **内容哈希**
  修改           就地覆盖            就地覆盖 + 日志      **产生新对象**
  历史           卷影副本（外挂）    快照（外挂）         **历史即结构本身**
  一致性         日志                日志                 **追加式 + 哈希校验**
  完整性         校验和              —                    **哈希即身份，全链路可验**
  去重           无（需重删）        无                    **白送**
  寻址           目录项 → MFT        dirent → inode       **引用（能力）+ 映射**

  ★ 关键推论：
    · "树"必须有一个根 → 而本系统**没有根**（公理 3）
    · "就地修改"会毁掉历史 → 而本系统**不可变**（公理 1）
    所以盘格式不可能沿用树，必须是图。

────────────────────────────────────────────────────────────────
二、HDGX 的布局（概念层）
────────────────────────────────────────────────────────────────

  ┌───────────────────────────────────────────────────────────┐
  │  超级块（带自校验）                                         │
  │     · 格式版本 · 块大小 · 指向"当前视图根"的引用             │
  │     · 采用双超级块 / 环形写入，保证崩溃后可恢复             │
  ├───────────────────────────────────────────────────────────┤
  │  对象区（只追加，永不原地改写）                             │
  │     对象 := [类型标签][长度][内容][内容哈希]                │
  ├───────────────────────────────────────────────────────────┤
  │  索引区  hash → 偏移                                        │
  │     索引本身也是对象 → 因此索引也可版本化、可校验           │
  ├───────────────────────────────────────────────────────────┤
  │  轴区（单调轴：只增不减）                                   │
  │     世代号 + 墓碑集合（已撤销的能力）                       │
  │     不属于任何态 —— 这是"权柄不可回退"的物理载体            │
  ├───────────────────────────────────────────────────────────┤
  │  视图记录区                                                 │
  │     每个视图一条：锚点集合 + 根映射引用                     │
  └───────────────────────────────────────────────────────────┘

  注意这里**没有**：目录项、inode、路径索引、空闲块位图（追加式不需要）、
  挂载表（没有根，所以没有"挂载"）。

  ★ 引导路径：
      固件 → 内核 → 读 HDGX 超级块 → 得到"初始视图根"
      → 按视图投影出可执行对象 → 运行
    **没有"挂载根文件系统"这一步** —— 因为没有根。

────────────────────────────────────────────────────────────────
三、包格式 .bao
────────────────────────────────────────────────────────────────

  ── 3.1 包是什么 ────────────────────────────────────────────

      deb     : ar 归档 = control 段 + data 段（文件树）
      ebuild  : 源码 + 构建脚本
      .bao    : **对象子图 + 映射建议**

      具体：
        包 = { 根对象引用（哈希）
               对象子图（该根可达的全部对象）
               映射建议（名字 → 引用，以及展示策略位）
               元信息（名字、版本说明、依赖引用） }

      ★ 包的身份就是它的根哈希。不需要额外的"版本号"来标识内容，
        版本号只是人读的标签。

  ── 3.2 安装是什么 ──────────────────────────────────────────

      deb     : 把文件拷到绝对路径，然后跑 maintainer scripts
      混沌    : **合并对象子图（去重）+ 把映射并入你的视图**

      于是安装动作只有两步：
        ① 对象区：有哪些对象还没有？只追加缺的那些（相同内容不重写）
        ② 视图：把映射建议合并进当前视图（冲突则需显式选择）

      ★ 因为对象不可变，安装**天然是幂等的**：
        装两次 = 第二次发现对象都在，只更新映射。
      ★ 因为内容寻址，安装**天然是完整校验**：
        任何一个对象哈希对不上，安装立即失败。

  ── 3.3 卸载 / 升级 / 回滚 ─────────────────────────────────

      卸载  = 从视图移除那些名字（对象仍在，直到 GC）
      升级  = 把映射指向新对象（旧态仍可回退）
      回滚  = 指回旧映射引用（免费，O(1)）

      ★ 三者都是**视图操作**，不涉及对象本身。

  ── 3.4 依赖 ────────────────────────────────────────────────

      依赖 = 被引用的对象（内容寻址）。
        · 不同版本 = 不同哈希 = 不同对象 → **天然共存，零冲突**
        · 相同内容 = 同一对象 → **天然去重**
      所以不需要"依赖解析器"，只需要"取缺失的对象"。

  ── 3.5 没有脚本 ────────────────────────────────────────────

      禁止 maintainer scripts / ebuild 这类任意代码。
      理由：
        · 脚本会破坏可回滚性（脚本的副作用不在对象图里）
        · 脚本是不可审计的黑箱
      替代：
        · 需要"配置"→ 通过映射与视图参数表达
        · 需要"生成文件"→ 在构建期完成，产物是对象

────────────────────────────────────────────────────────────────
四、最狠的结论：混沌不需要包管理器
────────────────────────────────────────────────────────────────

  作者原话："安装包是整体内核直接读取。"

  顺着这句往下推：

      安装 = 合并对象子图 + 合并映射
      而"存取对象"与"投影视图"本来就是内核的三机制之一

  于是：

  ┌───────────────────────────────────────────────────────────┐
  │  deb 需要 dpkg · rpm 需要 rpm · Gentoo 需要 portage        │
  │  **混沌不需要包管理器** —— 因为"安装"不是独立机制，         │
  │  它只是"合并映射"，内核自带。                               │
  └───────────────────────────────────────────────────────────┘

  还剩下的薄薄一层是什么：
    · 取源（从远端视图取对象）—— 就是三件套里的「取源」
    · 冲突选择（两个映射想占同一个名字时问用户）
    · 历史取舍（什么时候允许丢弃旧态）
  这三件事加起来不到一个"包管理器"的重量。

────────────────────────────────────────────────────────────────
五、抽象：一个结构覆盖七件事
────────────────────────────────────────────────────────────────

  作者要求："能抽象就抽象。"

  那个抽象就是三层：

      对象（内容寻址） → 映射（名字→引用） → 视图（可见世界）
                                    ↑
                          态（历史） · 轴（权柄）

  七件事全是它的不同规模：

      概念        就是
      ──────────────────────────────────────────────────
      包          一个对象子图 + 映射建议（可合并的视图片段）
      盘          对象区 + 索引 + 轴
      安装        合并（对象去重并入 + 映射并入视图）
      卸载        移除映射
      升级        换映射指向新对象
      回滚        指回旧映射
      系统        一个大视图 + 它的历史

  ★ 抽象到位的标志：**没有为任何一件事发明新机制。**
    本文从头到尾没有引入新的数据结构 —— 全是公理的直接后果。

────────────────────────────────────────────────────────────────
六、命名
────────────────────────────────────────────────────────────────

  系统名     **混沌 (HunDun)**
             名字本身极准：混沌是**未分化**的状态 ——
             没有全局根、没有目录树、只有对象与视图。

  盘格式     **HDGX**
             建议展开为 **HunDun Graph eXchange**
             理由：它的本质是**图**（DAG），不是树；
             而"与 NTFS/ext4 的区别"恰好就在这个词上。

  包格式     **.bao**（拼音"包"）
             与"关键字全用拼音"的体系一致。

七、诚实的难点（不回避）
────────────────────────────────────────────────────────────────

  N1  空间回收
      对象不可变 + 旧态永存（A35）与磁盘有限直接冲突。
      必须有 GC：引用计数（所有视图根 + 轴）+ 标记清除。
      ★ 但有一条铁律建议现在定下：
        **"丢弃历史"本身也必须是一条迹，且可审计。**
        你永远不能偷偷丢历史 —— 丢弃是一次显式、可查的操作。

  N2  追加式存储的写放大
      每次修改都追加 → 空间增长快。
      缓解：打包（对象分组）、小对象内联、批量提交。

  N3  索引的膨胀
      hash → 偏移 的索引会随对象数增长。
      缓解：多级索引（本身也是对象）。

  N4  崩溃一致性
      追加式 + 哈希天然一致，但"超级块指向哪个视图根"需要原子更新。
      缓解：双超级块 / 环形写入 / 末尾提交记录。

  N5  与旧世界互操作（对应待决 D7）
      必须能挂 FAT/ext4 并将其内容**投影成对象**（兼容视图）。
      否则 U 盘都插不上，系统无法落地。

  N6  大文件
      整个哈希对视频不友好 → 需要分块 + 树（blob 树）。

  N7  名字冲突与合并语义
      两个包的映射想占同一名字 → 需要明确的冲突策略
      （拒绝？改名？还是"视图里两个名字都保留，由引用决定用哪个"）
