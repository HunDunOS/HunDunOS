────────────────────────────────────────────────────────────────
零、为什么这条信息会改变优先级
────────────────────────────────────────────────────────────────

  我们现在的启动方式：

      qemu-system-i386 -kernel 内核.elf

  **这是 QEMU 专有的便利开关，真机上不存在。**

  真机必须走固件流程，于是四件事的优先级要重排：

  环节      QEMU 里                真机上                  优先级
  ──────────────────────────────────────────────────────────────
  引导      -kernel 加载 ELF       UEFI / BIOS 引导器      必须
  输出      串口（抓成文件）        **真机可能没有串口**    必须
                                   → 必须能显示到屏幕
  输入      TCP / 串口             **真实键盘**            必须
  存储      无                     真实硬盘（ATA/AHCI）    次之
  网络      e1000（QEMU 型号）     真实网卡型号不确定      最后

  ★ 结论：**显示与输入必须排在网络前面。**
    否则插上 U 盘开机 = 屏幕全黑、键盘无反应，什么也验证不了。

────────────────────────────────────────────────────────────────
一、三阶段
────────────────────────────────────────────────────────────────

  ── 阶段一：上真机的最小集（接下来的重点）──────────────────

      · framebuffer 文本控制台
          - UEFI 路径：用 GOP（Graphics Output Protocol）拿帧缓冲
          - BIOS 路径：用 VBE 的线性帧缓冲
          - 需要：8x16 点阵字体 + 字符绘制 + 滚动
      · PS/2 键盘输入
          - I/O 端口 0x60/0x64，扫描码表 → ASCII
      · UEFI 引导 + 可 dd 的 U 盘镜像
          - loader 读 FAT 分区里的内核文件，退出 boot services，跳转

      验收：插上 U 盘，开机，屏幕上出现"混沌"和一个能响应键盘的界面。

  ── 阶段二：有存储才像系统 ─────────────────────────────────

      · ATA PIO 起步（最简单），随后 AHCI
      · HDGX 最小实现：追加式对象区 + 索引 + 超级块
      · 笔编辑器的内容能写进盘、重启后读回来

      验收：打完字关机再开机，内容还在。

  ── 阶段三：网络与取源 ─────────────────────────────────────

      · e1000 先覆盖 QEMU；真机可能是 r8169 / e1000e / I219
        （要么挑型号，要么做多驱动，要么用 USB 网卡）
      · ARP + IP + TCP + HTTP GET
      · 取源：下载 .xy → 哈希校验 → 交给新语编译器编译

      验收：内核自己下载源码并编译运行。

────────────────────────────────────────────────────────────────
二、两个必须提前定的决策
────────────────────────────────────────────────────────────────

  ── 决策一：32 位还是 64 位？────────────────────────────────

    现状：新语编译器输出 **i386（32 位）**，QEMU 里验过的也是这套。

    选项 A：**先保持 32 位**
      · x86_64 CPU 向下兼容，能立刻上真机
      · 风险最小：QEMU 里验过的代码原样能跑
      · 代价：用不到 4GB 以上内存；看起来"不够现代"

    选项 B：**改成 64 位内核**
      · 要开 long mode：页表 + GDT + EFER + 64 位入口
      · 编译器要加 x86_64 目标（寄存器、调用约定、指令编码全都要动）
      · 这是个独立的大工程，会拖住"上真机"

    ★ 建议：**先用 32 位上真机把整条链跑通，再单独做 64 位。**
      不要把"上真机"和"上 64 位"绑在一件事里做 ——
      这正是我们核查过的项目栽过的那类错误（想一步做完）。

  ── 决策二：怎么引导？──────────────────────────────────────

    方案              优点                     代价
    ────────────────────────────────────────────────────────────
    自写 UEFI loader  U 盘即插即用；最干净；   要写 PE32+ 程序 +
                      完全属于自己             读 FAT + 退出 boot
                                               services（约 300–500 行）
    GRUB +           最省事，机器都认         需要在 PC 上装 GRUB；
    Multiboot2                               不算"自己的东西"
    bootboot         别人写好的 BIOS+UEFI      **要求 64 位内核**
                     双引导                    → 被迫先做 long mode

    ★ 建议：**自写 UEFI loader**。
      理由：
        · 符合"整条链都是自己的"这个目标
        · 是唯一能实现"dd 一下就能启动"的方案
        · 它本身就是一个值得写的里程碑（PE32+ 程序、FAT 读取、内存图）

────────────────────────────────────────────────────────────────
三、真机上的现实坑（提前知道能省很多时间）
────────────────────────────────────────────────────────────────

  P1  **Secure Boot**
      它会拒绝未签名的引导器。需要在 BIOS 里关掉
      （或自己签名，但那要额外的工具链）。

  P2  **没有串口**
      很多台式机主板有 COM 针脚但没引出；笔记本基本没有。
      所以调试输出必须上屏（这正是阶段一要做的）。
      ★ 建议：保留"双路输出"（串口 + 屏幕），哪边有就用哪边。

  P3  **CSM 与 UEFI 模式**
      有些主板默认关了 CSM（纯 UEFI），有些开着。
      自写 UEFI loader 只走 UEFI 就没这个问题。

  P4  **显卡**
      用 GOP 拿帧缓冲是标准做法，但要注意：
        · 帧缓冲可能是 BGRA 而不是 RGBA（要能识别并转换）
        · 有些固件只给很小的默认分辨率
        · 退出 boot services 之后必须继续用那块内存（不能重新分配）

  P5  **内存图**
      UEFI 给的 memory map 和 Multiboot 的完全不同，
      我们的"引导期分配器"要能吃两种输入。

  P6  **写盘风险**
      做 U 盘镜像时务必 `dd` 到**正确的设备**（`lsblk` 看清）。
      ★ 建议：脚本里加一道确认，并用"镜像文件路径"而不是裸设备名做默认参数。

  P7  **中断与 ACPI**
      真机要关机、要枚举设备，需要 ACPI 表（RSDP → XSDT → MADT/FADT）。
      阶段二再做。

────────────────────────────────────────────────────────────────
四、交付物调整
────────────────────────────────────────────────────────────────

  当前交付物（QEMU）：
      笔.elf 等 —— 只能用 qemu 的 -kernel 启动

  上真机后需要的交付物：
      · **可 dd 到 U 盘的 raw 镜像**（含 ESP 分区 + 内核 + loader）
      · 一个构建脚本：`sh 做U盘镜像.sh  输出.img`
      · 说明书：怎么写入 U 盘、怎么进 BIOS 选启动项、怎么关 Secure Boot

  ★ "dd 一下就能启动" 是这一阶段唯一的验收标准。

五、待决
────────────────────────────────────────────────────────────────

  Q1  阶段一的 framebuffer 分辨率策略（跟随固件？还是设固定值？）
  Q2  PS/2 扫描码表要覆盖多少（美式 101 键即可？还是要处理扩展码）
  Q3  UEFI loader 用哪种语言写（C？新语？）
      —— 权衡：新语还没有 64 位/结构体对齐/ABI 支持，
         而 UEFI 是 64 位调用约定（Win64 ABI）→ 建议 C 起步
  Q4  内核文件在 FAT 分区里的名字与位置约定
  Q5  是否同时保留 Multiboot2 路径（方便 GRUB 用户与 QEMU 调试）
  Q6  32 位内核在 UEFI 下如何进入（UEFI 先给 64 位环境，
      再切到 32 位保护模式？还是 loader 直接把 CPU 切到 32 位交付）
      ★ 这一条是阶段一真正的技术难点，需要先做个最小验证

────────────────────────────────────────────────────────────────
六、一句话
────────────────────────────────────────────────────────────────

  **"能上真机"不是"把 QEMU 里那套搬过去"，
  而是补上四件事：引导、显示、输入、存储。
  而这四件里，显示和输入必须最先做 —— 因为没有屏幕和键盘，
  你连"它启动了"都不知道。**
