        编译器入内核：机制、风险与裁决   v0.1
      （作者设计意图："编译器写在内核里，编译内核时顺便编译进去"）
════════════════════════════════════════════════════════════════

────────────────────────────────────────────────────────────────
零、作者意图的确切含义
────────────────────────────────────────────────────────────────

  作者原话："将来你是要把它写在内核里面的这个编译器。以后编译这个
             那个内核的，他也会顺便编译进去。"

  翻译成设计语言：

    内核镜像里**内置一个可用的编译器**；
    构建内核时，编译器被一起编译并链入镜像；
    于是内核**具备重建自己的能力**。

  这不是妥协，这是前文《自重建内核》那条准则的必然结果：

      内核准入准则：内核只装"重建整个系统所必需、且不可再分"的东西。
      → 编译器正是那个"所必需"。

────────────────────────────────────────────────────────────────
一、"顺便编译进去"的机制
────────────────────────────────────────────────────────────────

  ── 1.1 首次构建（宿主参与）────────────────────────────────

      内核源码.xy    ─┐
      编译器源码.xy  ─┼─► 用宿主 stage0 编译 ─► 目标代码 ─► 链成镜像
      最小运行时     ─┘

      产出的内核镜像包含：
        · 三机制（态 / 迹 / 视）
        · 编译器（目标代码）
        · 最小运行时
        · **内核自身的源码对象**（重建的原料）

  ── 1.2 之后的每一次 ───────────────────────────────────────

      镜像自带的编译器可以：
        · 重新编译它自己  → 语言自举在系统内完成
        · 重新编译内核    → 系统自重建（断言 A23）

  ── 1.3 鸡与蛋 ─────────────────────────────────────────────

      时刻            谁提供编译器
      ────────────────────────────────────────────
      首次构建        宿主（C 写的 stage0 / 已实现）
      此后每一次      **镜像自带的编译器**

      这就是自举链的闭合方式，也是 A57（删掉 xyc.c 仍可重建）的意义。

────────────────────────────────────────────────────────────────
二、三个风险（都是我们核查过的项目栽过的坑）
────────────────────────────────────────────────────────────────

  R1  编译器是"解析不可信输入的巨型攻击面"
      → 放进内核，等于把这个面抬到最高权限
      → HaoOS 那类项目"什么都往内核塞"的典型后果

  R2  体积与耦合
      → 内核变得不可审计，职责混杂

  R3  崩溃影响
      → 编译器崩了不应该带走内核

────────────────────────────────────────────────────────────────
三、裁决：编译器在内核里，但不以全权运行
────────────────────────────────────────────────────────────────

  ┌────────────────────────────────────────────────────────────┐
  │  编译器是内核里的一名「分身」，不是内核的一段代码路径。      │
  │                                                            │
  │      本源 ──签发──► 编译分身                                │
  │                       · 只能读：源码对象                    │
  │                       · 只能写：输出对象                    │
  │                       · 不能碰：态的其他部分、能力轴、       │
  │                                  其他分身                   │
  └────────────────────────────────────────────────────────────┘

  为什么这个裁决成立：

    · "在内核里"满足的是**体验**（开机即编译，不依赖外部工具）
    · "换不了权限"满足的是**安全**（攻击面造成的损害被限制在一个分身内）
    · 两者不冲突 —— **因为本系统有分身模型与能力对象**。
      别家的内核做不到这一点，因为他们没有这套机制。

  R2 的处理：
    编译器与三机制**通过对象接口交互**，不做内部耦合。
    它不是"内核的一部分代码"，而是"内核里的一个居民"。
    判断标准：把编译器整体删掉，三机制仍应完整可用。

  R3 的处理：
    编译器运行在受保护的分身内；编译失败只应产生"错误对象"，
    不应影响内核。早期若做不到完全隔离，至少要保证
    "编译失败 = 产生一个失败对象"，而不是崩溃。

────────────────────────────────────────────────────────────────
四、必然推论：编译 = 一条迹（这是别人给不了的）
────────────────────────────────────────────────────────────────

  因为内核自带编译器，且系统以"态"为单位：

      源码对象 ──编译──► 目标对象
            └── 一次「态 → 态」的转移 ──┘

  于是：

    性质              为什么免费（来自哪条公理）
    ──────────────────────────────────────────────────────────
    每次编译可回滚    公理 1（不可变）+ 公理 7（变更原子）
    每次编译可审计    迹本身是对象，可哈希、可追溯
    构建可复现        A16（同源码 + 同编译器 → 同哈希）
    编译历史可查询    "这个内核是哪个源码、哪个编译器编的" → 图查询
    编译器本身可回滚  编译器也是对象，可版本化

  ★ 对比：在主流系统里，编译是"跑一条命令、产生一个文件"。
    在本系统里，**编译是系统内部的一次可追溯事件**。

  ★ 再进一步：既然编译是迹，那么"内核是如何被造出来的"这个问题，
    答案本身就是系统里的一个对象 —— 系统记得自己的来历。

────────────────────────────────────────────────────────────────
五、对自举路线图的修改
────────────────────────────────────────────────────────────────

  原 M6：删掉 xyc.c，仅用 .xy 源码重建
  → 拆成两步：

  M6  删除 xyc.c 后，项目仍能仅凭 .xy 源码重建
      验收：在没有 C 编译器参与的情况下完成一次完整构建

  M7 【新增】编译器入内核
      验收：
        a) 构建出的内核镜像里，编译器可用
        b) 在内核内调用编译器编译一个 .xy 程序，结果从串口输出
        c) 编译产生的是一条迹（可见、可哈希、可回滚）
        d) 把编译器整体移除后，三机制仍完整可用（验 R2）

  顺序不变：**语言先自举（M6）→ 编译器入内核（M7）→ 系统自重建（A23）**

────────────────────────────────────────────────────────────────
六、新增可验证断言（接 A1–A58）
────────────────────────────────────────────────────────────────

  A59 [编译器在镜像内]
      内核镜像中可定位到编译器，且能在内核内调用并产生正确结果

  A60 [编译是迹]
      一次编译产生一个迹对象；该迹可哈希、可由其重建输出；
      篡改迹 → 校验失败

  A61 [编译器低权]
      编译分身尝试访问能力范围外的对象 → 必须失败

  A62 [解耦]
      把编译器整体移除后，三机制（态/迹/视）仍完整可用

  A63 [来历可查]
      对任意一个目标对象，可查询出"它是哪个源码对象、由哪个编译器
      对象编译而来"的完整链路

  ★ A62 是"内核是否被污染"的检查：
    它把"编译器是居民而不是内核代码"这句设计主张变成可跑的验收。
  ★ A63 是本系统独有的能力：**系统记得自己的来历。**
